# 0.46.0

MAS 提出ワークフローの冪等化と信頼性改善 (issue #615)。0.45.0 の提出で
«Archive and upload が 2 時間でタイムアウトし cancelled» «提出済みの版への
apply 再実行が HTTP 409 で failure» «conclusion だけ見ると提出の実状態を誤認»
という 3 つの不具合が再発したため、提出まわりの信頼性を上げた。
**アプリ本体の機能変更はありません** (0.27.0 / 0.43.0 の前例どおりの
メンテナンス版。録画・文字起こしの挙動は 0.45.0 から変わりません)。

## MAS 提出ワークフロー (mas.yml) の冪等化

- upload / apply / submit の各段階の前に ASC の実状態を照会する preflight
  (`scripts/release/mas-state.py`、**読み取りのみ**) を追加。版の state と
  build の processingState を GitHub Actions の step outputs として出す
- 提出済み以降の版 (WAITING_FOR_REVIEW など編集不可の状態) への apply / submit
  再 dispatch は、何もせず **success で終わる**。0.45.0 で
  «WAITING_FOR_REVIEW の版に build 割当て PATCH → HTTP 409» で failure になった
  実測 (run 44795636897) の再発を止める。途中再開でも二重提出を作らない
- upload は指定 build が ASC に既に存在すればアーカイブをやり直さず
  **再利用する** (FAILED / INVALID の build は同じ番号で再アップロードできないため
  その場合は番号を増やすよう明示して失敗)
- upload の後に ASC 上で build が **VALID** になったことを poll で確認する。
  «アップロードできたか» の判定をワークフローの conclusion ではなく
  **ASC 実状態** で行う (0.45.0 の教訓の機械化)

## Archive and upload の停滞検知 (watchdog)

- 0.42.0 以降、CI の upload が CodeSign あたりで沈黙し job 上限
  (60 → 120 分、#589) まで費やして cancelled になる事故が続いた
  (0.45.0 の run 44791492122 は最後のログ出力から正味 2 時間、1 行も進まず)。
  timeout-minutes の延長は «ハングを長く観察する» だけなので、次の一手として
  watchdog を追加した
- スクリプトの出力を退けた上で 1 分ごとに経過時間と最新行を job ログへ出し
  (進捗の定期出力)、**無出力 12 分** でハングとみなして打ち切り、上限
  **70 分** でも打ち切る。打ち切りは明示的な失敗として、診断行と
  ローカル経路 (0.43.0 / 0.44.0 / 0.45.0 の前例) への切り替え案内を残す
- 根本原因 (Apple Development 証明書まわり、#470) の調査は別途 — この版は
  «ハングを 2 時間観察しない» ことにだけ責任を持つ
