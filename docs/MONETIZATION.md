## 1. この文書について

kilde を個人開発として継続する上でのマネタイズ方針の判断材料とするため、
同種アプリ (画面録画 / 音声録音 / 会議 AI ノート / OSS 収益化) の成功事例を
調査・整理した。対象 issue: #104。

## 3. kilde の位置づけと差別化

kilde が刺さる隙間 (Section 2 の事例との対応):

- **QuickTime ができない「システム音声 + マイクのミックス録音」を 1 コマンドで** —
  従来の解は Audio Hijack ($69) か BlackHole + Audio MIDI Setup 手動構成 + QuickTime/OBS
  という面倒な組み合わせしかなかった (DESIGN.md §1 と同旨)
- **会議録画**という最重要ユースケースは、2026 年に最も金が動いている領域
  (Otter / Fireflies / tl;dv は $10〜19/ユーザー/月で稼いでいる)
- **「Ctrl+C でも必ずファイナライズ」の信頼性**と**ローカル録画 (会議にボットを
  入れない)** は、クラウド型競合に対するプライバシー・信頼上の差別化になる
- 汎用の美麗デモ録画 (Screen Studio の土俵) は Red Ocean。kilde は
  「開発者・技術者向けの会議・音声録画 utility」という **Audio Hijack 型ニッチ**にいる

## 4. 提案 — フェーズ別マネタイズ戦略

ロードマップ (M1〜M3) に紐づけた段階的な案。各フェーズの判断は依頼者が行う。

### Phase 1 (現在〜M2): 収益化ではなく導線を築く

- CLI は**永久無償 OSS** と明言し、GitHub Sponsors を設置するだけ
- Homebrew tap (issue #24 相当) と Releases 署名が fan-out の武器
- Show HN / Reddit (r/macapps) / 日本語圏 (Zenn・Qiita) でローンチして star を貯める。
  star 数と Homebrew インストール数が後の販売資産

### Phase 2 (M3 GUI リリース): open core 二層化 (Cap モデル)

- KildeCore + CLI = OSS 無償のまま
- **kilde GUI = 有償**。価格は CleanShot 型「$29〜39 買い切り + 1 年更新込み、
  以降 $19/年 (任意)」を推奨 (§2.1 参照 — 完全サブスクへの移行は不評の定番)
- 商用利用の有償化を検討する場合の注意: kilde の現行ライセンスは **MIT** で商用利用を
  無償で許諾しているため、商用だけ有償にすることは現行ライセンスでは実行できない。
  実施するにはデュアルライセンス化などの**ライセンス変更**とコントリビューター同意
  (CLA) が必要で、MIT で配布済みの既リリース版には遡及適用できない。
  OSS としての信頼 (Phase 1 の方針) との兼ね合いも要検討。
  なお参考例の Obsidian は OSS ではなく独自ライセンスのフリーウェアである点に注意

### Phase 3: Pro サブスク ($8〜12/月) — AI レイヤーで LTV を上げる

- 録った会議の**文字起こし・要約・共有リンク**を Pro に。Raycast / Warp に見る
  「コア無料、AI が課金の柱」の現行スタンダード
- 売り文句は「**会議にボットを入れない。録音はローカル、AI 処理だけクラウド**」—
  Fireflies たちに対する明確な差別化
- AI コストを避けたい下位プランには BYO API key (ユーザーの OpenAI/Anthropic キー)、
  ホスト型を上位プランにする選択肢もある

### Phase 4 — 補助戦線

- Setapp 収載: リリース直後に約 30K imp の初期露出が得られる (CleanShot も採用)。
  収益分配は利用シェア制なので、直接販売との併用が前提
- 長期視点: Audio Hijack が証明するように、代替不能な音声 utility は
  **買い切りで 20 年売れ続ける**。急がずメジャーバージョン課金で細く長く

## 5. 避けるべきパターン (事例から裏付けあり)

1. **CLI の有償化** — 導線と信頼が死ぬ (Phase 1 の設計と矛盾)
2. **完全サブスク一本化** — Screen Studio の移行不評が教訓。買い切り+更新の
   CleanShot 型が Mac utility 圏では最も安全
3. **収益化ゼロのまま継続** — Kap の二の舞。GUI (M3) のモチベーション維持にも悪影響

## 6. 現実的な期待値

- フリーミアムの有償転換率 (無償ユーザーを分母とした、個人ユーザーのアップグレード率)
  はセルフサーブ B2B SaaS で 2〜5% が中央値との調査 (OpenView/Pendo、1,000+ 製品) があり、
  開発者向けツールはさらに 1〜3% 側に寄るという報告が複数ある。
  つまり収益は無償ユーザー数に比例し、**Phase 1 (導線構築) の比重が実際は一番大きい**
- 個人開発で生活が成り立つのは上位一握り。副業規模で始めて、M3 GUI の手応えで
  踏み込む深さを決めるのが現実的

## 8. 方針決定 — Pro の判定・ライセンス検証を private エンジン側に置く (issue #168、2026-10-17)

依頼者が «収益化が見込める選択をあなたがしてください» と選定を委任したため、
エージェントが決定した。選択肢は «寄付的課金 (全コード公開のまま判定も公開コードに置く)»
か «Pro の実装・判定を private エンジン側に置く» だった。

### 決定

**«Pro を private エンジン側に置く» を採用する。** Pro の判定・ライセンス検証の本体を
private の KildeCore (kilde-team/kilde-cli-swift) に置く。GUI (このリポジトリ, MIT・公開)
は公開のまま変更しない。

### 理由 (まず選択肢の前提を揃える)

A («寄付的課金») は «Pro の判定を公開の GUI コードに置く» こと。エンジン自体は private の
ままでよい (エンジンまで公開して初めて «全コード公開» の真の honorware になるが、それは
#168 が提示した選択肢の外)。この前提で比較する。

1. **近い将来の実効性は A ≒ B**: GUI は private SPM 依存 (エンジン) なしにはビルドできない。
   したがって A («判定を GUI に置く») でも自己ビルドによる解除は現状ほぼ不可能で、
   実効性の差は小さい。決め手は以下の差分
2. **MIT コードの純粋さ**: A は公開の MIT コードに課金判定 (DRM) を混ぜる — «open-source»
   表記との不整合が生まれ、§3 の «信頼» という差別化を傷つける。B なら公開コードは
   DRM フリーのまま (gui/ の MIT としての権利は変更しない — «課金の対象» を参照)
3. **将来の頑健性**: エンジン依存の形が変わる・将来エンジンを公開する場合でも、エンジン内の
   ゲートは残る (A の GUI 側ゲートは外れる)。以降の Pro 機能をエンジン側に追加していく
   場合も、判定の一元化は B の方が素直。B は既存構造 (エンジンは分離時点から private で
   README の表にも明記済み) に判定を置くだけで、新たな非公開領域を増やさない
4. **前例**: §2 の表には寄付的課金で持続した事例が挙がっておらず、収益化ゼロで開発が
   緩慢になった Kap が対照例 (§5.3)。最も構図が近い Cap は Desktop License ($29/年) を
   課している (§2.3)
5. **チャネルと将来性**: 一次チャネルの MAS はバイナリ配布のため A/B の実効差は小さいが、
   DMG 直接販売 (#172) と法人 (フェーズ 4 — ABM/MDM のボリュームライセンス) には
   実在するライセンスが必要。B はこの将来の選択肢を閉じない
6. **差別化の保護**: ライセンス検証は**オフラインで完結**させる (MAS: StoreKit 2 の権利確認 /
   DMG: 署名検証つきライセンス鍵)。サーバー確認・電話ホーム・テレメトリは行わない —
   «ボットなし・クラウドなし・ローカル完結» (§3) の差別化を損なわない
7. **増分工数が小さく、逆方向の移行は大工事**: #169 (StoreKit) / #170 (ロック UI) は A でも
   必須。B の追加分はエンジン側のゲート API とオフライン検証のみ。A で始めて後から
   機能をエンジンへ移すのは大工事で、将来「緩める」のはいつでもできる

### 課金の対象 (MIT との整合)

MIT で公開している gui/ ソース自体の権利は変更しない (商用利用を含む)。課金の対象は
«リリース物 (アプリバンドル) に含まれる Pro 機能の利用権» — Cap の open core (§2.3) と
同じ構図。«MIT なので商用だけ有償化できない» という §4 Phase 2 の注意は、この
«ソース (MIT) / 配布物の Pro 権 (課金)» の切り分けで解消する。README の open-source
表記は本決定に合わせて実態どおりに更新した。

### 線引きと価格 (2026-10-17 に確定 — issue #168)

依頼者の委任 («あなたが適切に判断して作業を進めてください») を受け、下記のとおり確定した。
実装 (#169) 着手前に実績データで見直す場合は本節を更新する。

- **線引き**: 本方針 (判定をエンジンに置く) では、**公開 GUI に実装済みの機能をそのまま
  Pro 化することはできない** (ゲートが公開コードに現れるため。エンジンへの移行が前提)。
  この制約を踏まえると:
  - **第一弾の Pro = 要約 (#163)** — エンジン実装済み (kilde-team/kilde-cli-swift#40) で
    本方針と両立する唯一の候補。«AI が課金の柱» (§2.2) とも合致する
  - **第二弾の Pro = フォローアップの下書き (kilde #464 / エンジン kilde-cli-swift#137、
    0.28.0)** — 要約 (要点・決定事項・アクション) から参加者へ送るメッセージの
    下書き (メール / チャット) をエンジン新機能として生成する。«以降の Pro 拡張は
    エンジンに実装する新機能» の第一例 (2026-10-29 の «次バージョンに必要な機能»
    選定 — 依頼者の委任によりエージェントが決定)。**kilde.pro の買い切り 1 商品は
    Pro 全機能のライセンス** のまま (既存購入者への追加提供、新 IAP は作らない)
  - **無料に留める**: 録画 / 文字起こし / **会議の自動検出 (#162 — 既に無料機能として出荷済み
    で App Store の説明文でも無料と案内)** / ライブラリの閲覧と再生・全文検索 (#165) /
    書き出し先の連携 (#164) / ショートカット (#167) / 録音の告知文コピー (#166) / CLI 全機能。
    CLI の有償化はしない (§5.1)
  - 以降の Pro 拡張は «エンジンに実装する新機能» で検討する。GUI 実装済み機能の Pro 化は
    エンジン移行コスト込みで個別に判断する
- **価格・形態**: MAS で買い切り **¥2,800 前後**とする (§2.1 の CleanShot 型が近い)。完全
  サブスクは避ける (§5.2)。直接配布販売 (#172) は当面見送り、MAS の実績を見てから
  改める。Setapp (#173) も MAS のデータが揃うまで保留
- 実装の着手はフェーズ 2 (#161) の出口条件達成後 (#174)。#171 (寄付導線) のみ先行可 —
  エピック #174 自身が «先行してよい» と定めているため
  技術設計 (StoreKit 2 / 署名鍵の検証をエンジンのどの層に置くか) は
  kilde-team/kilde-cli-swift に設計 issue を起票して進める

### 第二弾 Pro の追加 (2026-10-29 — «次バージョンに必要な機能» の選定)

依頼者指示 «v0.27.0がリリースされたので、次バージョンに必要な機能を実装し、
AppStoreに申請してください» (2026-10-29) に対する選定。実装可能キューの監査

レビュー 0 件でユーザー発のシグナル無し) の結果、**本 §8 が予定する «エンジンに

転換 2% (エピック #174 の出口条件) に向けて Pro の価値を増やす余地が大きい)。

(kilde #464)。¥2,800・IAP 1 商品・既存購入者への追加提供は不変。
